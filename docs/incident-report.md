# 事件经过与系统实际环境

本报告只描述本台 NAS。时间均为 Asia/Shanghai（UTC+8）；初版环境核对截至 2026-10-29 18:00，后续补充核对截至 21:28，恢复状态另保留 20:20 检查点。设备在公开文档中称为 **NAS-A**，个人共享目录和文件名不公开。

## 环境核对

两个系统版本文件均显示 DSM 7.2.1-69057、`smallfixnumber=1`，内核为 4.4.302+，x86_64。DSM 的启动信息报告型号 DS918+，但 DMI 显示 OEM 厂商信息、产品名 Synoden，CPU 是 Intel Celeron J1900。型号标识与硬件并不一致，所以本报告不把设备描述为已验证的原厂 DS918+。

CPU 信息未报告 `hypervisor` 标志，检测工具 `systemd-detect-virt` 不存在。后续所有者已明确确认 DSM 直接运行在物理机上；本报告将所有者确认与硬件型号的独立验证分开记录。本次采集在 DSM 内进行，没有使用 PVE/QEMU 管理接口或宿主机 RAM 快照。

最初排查时系统已连续运行约 26 天。现场有两个 Btrfs 卷，主要受影响共享目录观察到 NOCOW 标志。没有找到已确认可用于回滚的用户数据快照；Docker 相关子卷或快照不能充当用户文件备份。NOCOW 会降低依赖旧数据块版本的恢复机会，但不等于已证明全盘所有旧数据都被覆盖。

## 发现与保全

大量文件带 `.L0CK3D` 后缀，存在 `read-me3.txt` 勒索信，与 C3RB3R 命名特征吻合。这里采用“C3RB3R 事件”作为案件标识，不据此认定它与任何公开案例使用同一加密器或同一密钥。

SSH 初期受到大量未认证连接影响，触发 `MaxStartups`。建立稳定管理连接后，排查时未发现仍在运行的加密进程，也未取得加密器可执行文件。这降低了直接从活动进程提取材料的机会，但进程列表本身不能证明系统已经清洁。

从 `/proc/kcore` 顺序读取物理内存映射，向分析机流式保存，共 8,479,907,840 字节。另保存 `/dev/md1` 和四个 zram 设备的可读副本。采集时系统继续运行，SSH、sudo、采集程序均会改变现场；这些数据不是同一时刻的原子镜像。原始副本只在私有取证目录保存。

## 恢复和处置动作

| 阶段 | 实际动作 | 对结论的限制 |
| --- | --- | --- |
| 初期 | 盘点进程、存储、勒索信和样本，先保存内存及交换数据 | 操作会产生系统日志，没有把在线系统冻结为不可变现场 |
| 密钥分析 | 在副本上验证多类候选与参考项目公开材料 | 无有效命中，不能写成解密成功 |
| 残存数据提取 | 检查归档内部可读成员、Office 组件、媒体片段和地图区块 | 同一原文件可能产生多个输出；缺失部分没有因此恢复 |
| 历史数据 | 从可读的 Btrfs 历史根提取一批项目文件 | 仅局部历史内容，未证明恢复整个应用 |
| 已知驻留处理 | 先保存脚本和配置，再隔离下载脚本、移除精确匹配的 cron 与启动调用 | 仅处理已确认条目，未完成固件及全系统完整性验收 |
| 后期恢复 | 在 NAS 上部署恢复服务，将结果写入新目录，校验任务断点续跑 | 原加密源文件在所测任务中保持摘要与元数据不变；新目录写入仍会占用原卷空间并可能覆盖空闲历史块 |

已知下载脚本最初于 14:35 左右改名停用，约 17:19 在保留证据后进一步清除其已识别的 cron 和启动引用。约 17:08 停止原有 FRP 客户端；FRP 服务端已由所有者确认是合法自建中继，停止它属于当时的通道处理，不能倒推它是恶意软件。

17:43 左右的服务验收记录显示恢复任务启用并运行，父进程为 PID 1。一个测试任务在 4 MiB 检查点停止后恢复并完成，对应原密文文件的全文件 SHA-256 和元数据保持不变。这只能证明所测任务的行为，不能替代全部任务的逐文件审计。

后期恢复目录改为保留来源层级；19,916 个早期输出迁移时检查了 inode 和大小。目录更易查找，并没有修复已经丢失的内容。

## 没有完成的事项

没有完成全盘取证镜像；没有找到经验证可用的解密密钥；没有确认攻击者真实入口 IP；没有还原完整原始利用请求、恶意 cron 文件内容或加密器本体；没有对所有输出完成原应用验收。恢复仍在继续，因此所有数量都对应明确检查点。

后续还取得在线根系统分区镜像及疑似相关的 UPX 首块残片，并重建了与恶意任务关联的调度进程部分地址空间。完整样本、全盘镜像及一致进程转储仍未取得，详见[后续调查](follow-up-20261029.md)。
