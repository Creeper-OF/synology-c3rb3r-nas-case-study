# 内存采集与密钥验证

本案的关键结果是**尚无候选通过本机密文验证**。候选结构、字符串和数十亿次测试本身都不是解密成果。

本页下表保留初版的早期检查点。[后续调查](follow-up-20261029.md)新增了 24,120 份文件尾语料、物理机参考项目实测、36 字节和尾轮残片、编码材料及换出页边界验证，也更正了 zsmalloc 类字段、重复页计数和本机交换 PTE 编码。

## 采集方式与限制

现场允许读取 `/proc/kcore`，据其映射向 NAS 之外顺序保存了 8,479,907,840 字节的物理内存区域，另外保存交换设备。不是直接把巨大的 kcore 虚拟文件尺寸当作实取 RAM 数量，也没有取得同一时刻的全系统快照。

采集开始时未找到活动加密进程。已退出进程的页可能被重用；系统、SSH 和其他应用也会产生 AES、ChaCha 或 RSA 数据。发现类似结构只能进入候选集，必须用本机密文和可检验的格式约束验证。RAM 中没有某个签名，不能证明某个程序从未运行。

以下记录使用各自候选生成器和去重规则；不同扫描的数量不相加。

早期扫描曾产生不同数量的临时候选。另有一次 AES 候选生成器出现负移位错误，修复并验证后重跑；旧输出不作为有效结果。后续也发现早期 4.4 与本机 4.4.302 的交换页编码不同，旧交换映射检查不能作为有效排除；修正后已重做。计数均按阶段、数据表示和各自去重规则解释。

## 为什么参考项目不能直接解密本案

本次核对固定在 [soimy/c3rb3r-rescue 的 130933a](https://github.com/soimy/c3rb3r-rescue/tree/130933a95bf823bafc998a9d122b055075660319)。隔离环境中，其 24 项测试通过；这只验证相应测试样本，不证明本案文件适配。

五个本机样本均观察到尾标记 `6d147f60`，参考案例公开配置为 `ce35a593`。按参考代码字段解释的其他值不等于已独立逆向本案格式。公开材料的记录 nonce 检查没有通过，参考代码的精确签名也未在已扫描副本中发现。

没有修改尾标记检查来强行运行。相同 588 字节尾部长度、勒索信或后缀，均不足以证明密码算法、分段策略或密钥相同。本案没有取得加密器本体，因此没有独立确认其完整密码实现。

## 阴性结果的含义

结果只能表述为：“在已保存副本和已实现假设中未找到有效密钥。”它不能证明内存从未存在密钥，也不能证明任何其他布局、密钥派生方式或未来分析都不可能成功。

本次可提取的完整成员来自仍可读取的数据区域，并非上述候选成功解密。内存候选和私钥可能属于正常服务，均留在私有目录，不随公开案例发布。

证据对应 [E04–E06、E14–E17](../evidence/evidence-index.json)。
