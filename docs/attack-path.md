## 本机的关键残片

在内存采集文件 `ram-08-100000000.bin` 的**文件内偏移** `4993348294` 找到以下连续文本。该偏移不是 NAS 物理地址：

```text
LD_DEBUG_OUTPUT=/etc/cron.d/synotgzz
ESCAPE=PLUGIN_VALUE_START
NOP]. [0x1D00 user_db_get.c:36]
```

附近还有 `synoscgi_SYNO.API.Auth_7_login[18507]` 报错残片，但日期前缀被截断。无法给它指定完整时间，也不能因其他日志出现同号 PID 就视为同一进程；PID 会复用。

上面的 cron 路径与 05:03 删除调用中的前缀一致。Rapid7 的[原始研究，第 5 页及 DSM 案例部分](https://assets.contentstack.io/v3/assets/blte4f029e766e6b253/bltad0709de42b54e82/689604359f008cdd02f69917/disguise-delimit-whitepaper.pdf)解释了 `LD_DEBUG_OUTPUT` 输出名附加 `.PID` 的行为，以及 DSM 插件环境变量注入到 cron 执行的机制。两者的组合具有指向性，超过“内存里出现普通动态加载器字符串”这一弱线索。

实际版本为 DSM 7.2.1-69057 Update 1，低于厂商对该分支列出的修复版本 Update 6。[Synology-SA-24:20](https://www.synology.com/en-global/security/advisory/Synology_SA_24_20)将 CVE-2024-10441 描述为系统插件守护进程相关的远程代码执行漏洞。

**判断：现有证据强烈支持与 CVE-2024-10441 一致的利用路径。** 这是结合本机残片、版本和公开机制的推断。缺少完整请求、落地 cron 内容、载荷本体和连续进程链，不能宣称全部攻击步骤已经被逐项证实。

## 较早的驻留线索

发现隐藏下载脚本 `/etc/.conf`，SHA-256 为：

```text
5dc595d955cc5b268f7d40e36eb6ed22005fee2efdc64eab5029df5a71fd7d0f
```

脚本包含下载执行、检查进程和写入持久化引用的逻辑；对应引用出现在 cron 与 `/etc/rc.subr`。原始 cron 条目在通常的系统 crontab 格式下缺少用户字段，因此不能仅凭“每 20 分钟”的表达式就认定它在该环境成功按周期执行。

脚本 mtime 指向 2026-01-09，异常启动引用所在文件时间戳指向 2026-01-14。这提示可能存在更早驻留，但文件时间可以被修改；没有证据把它、当天的加密和同一个攻击者完整关联。下载脚本本身也不等于已经取得加密器。

另观察到若干 root 身份、可执行文件标记为 deleted 的 BusyBox/inetd 进程。启动时间、文件状态和监听端口是调查线索，尚不足以将这些进程全部判为恶意。

## 为什么还不能给出攻击者 IP

NAS 使用所有者自建的 FRP 中继，部分 DSM/SSH 认证日志只记录环回地址。合法中继服务器地址不是原始攻击来源。现场后续还出现过外部失败认证及转发记录，但没有证据把它们与凌晨的利用和加密关联。

因此公开报告不列出“疑似攻击者 IP 清单”，也不把合法云服务器、中继地址或普通扫描来源贴上攻击者标签。

尚缺中继端当时的 frps 日志、反向代理访问记录或已保留的云流量记录。只有日志当时已启用、保留了真实来源和时间字段，才有机会继续关联。当前数据中没有足以完成该关联的成功登录记录或完整利用请求。现在开启的新日志不能补回过去未记录的来源。
