# 一台 DSM NAS 的 C3RB3R 事件：取证、密钥验证与残存数据恢复

这是 2026 年 10 月 29 日一台 NAS 遭遇 `.L0CK3D` / `read-me3.txt` 勒索事件后的实机处置记录。由设备所有者授权公开，参考 [soimy/c3rb3r-rescue](https://github.com/soimy/c3rb3r-rescue)，根据本机证据独立整理。

**本案尚未找到可用解密密钥。已取得的结果主要来自未加密区域、归档成员、历史数据和片段重建。输出数量不能代表完整文件恢复数量，更不能代表恢复率。** 所有者反馈部分结果已经“面目全非”；这份记录保留这一结果，不把格式检查通过写成业务恢复成功。

本次补充包含 **2026-10-30 00:29 的内存封存结果，Asia/Shanghai（UTC+8）**；恢复数量保留历史检查点，新增 **22:46:35 状态检查点**。本仓库不是实时进度看板。

越南 NAS 网站 [Nashub](https://nashub.vn/posts/synology-ransomware-c3rb3r-lock3d) 在 10 月 29 日标注为 19:08 的更新中链接本仓库，列作本轮事件的第四个公开取证案例，来源标注为受害者自述。技术结论仍按本仓库的证据和验收口径说明。

本轮新增内容见[后续调查与方法修正](docs/follow-up-20261029.md)：关联到调度进程的恶意任务残片、外部节点 S1 的连接与下载线索、交换页编码修正、换出页边界重组，以及仍未命中的密钥验证。

本轮重点见 [ext4 补查](docs/ext4-ioc-follow-up-20261029.md)：已释放的来源属性块命中独立公开的精确投递 URL，明文 `rm.log` 证实此前内存中的清理调用；更早 journal 与现有副本去重得到 247 个 inode 版本，仍未找到原始 `libgld` inode。新增 [晚间密钥验证](docs/late-key-validation-20261029.md)全部未命中。相同端点不能单独确定精确批次或操作者。

新增 [引导检查与 05:00–10:00 磁盘记录补查](docs/boot-and-disk-window-20261029.md)：引导分区、分区表及选定启动组件未见本轮破坏证据，已另存九份加密日志的明文追加尾部；时间线补充了多项应用与日志服务故障。

新增[攻击来源与全程时间线](docs/attack-reconstruction-20261030.md)和[NAS 本地内存封存报告](docs/memory-preservation-20261030.md)：展开关联节点、DSM 登录插件/cron 执行链的证据与推断，并记录第二次采集、完整声明 RAM 覆盖、校验和只读封存。未新增业务资料恢复细节。

新增[今早投递节点、完整样本和密码学复核](docs/payload-node-review-20261030.md)：已取得外部完整样本，5 对核心文件与凌晨保留件逐字节相同；首块残片匹配但仍缺 NAS 原始全文件摘要。补充节点路径的 200→404 时间线，并修正公钥提取和轮数判断。没有新增有效密钥或解密成功。

已按所有者后续明确授权发布[研究样本附件](docs/research-samples.md)：11 份真实恶意样本及脱壳产物放在独立的[加密 Release](https://github.com/Creeper-OF/synology-c3rb3r-nas-case-study/releases/tag/research-samples-20261030)，公开密码 `infected`。**样本可能加密或破坏数据，仅供隔离环境中的防御研究，禁止在生产系统执行。** Git 历史不保存这些二进制或脚本。

## 本机情况

| 项目 | 实测结果 |
| --- | --- |
| 系统 | DSM 7.2.1-69057 Update 1，Linux 4.4.302+，x86_64 |

| 内存采集 | 直接从 DSM `/proc/kcore` 顺序采集 8,479,907,840 字节，另采集交换设备；不是原子快照 |

| 密钥与样本 | 排查时未发现活动加密进程；后取得外部完整样本，其前 4096 字节与 NAS 保留残片匹配；NAS 当时全文件摘要仍缺，密钥验证未命中 |
| 入侵路径判断 | 内存残片强烈支持与 CVE-2024-10441 一致的 DSM 登录插件环境变量注入；攻击链尚未闭合 |
| 来源关联 | 已关联外部节点 S1 的既有管理代理连接、下载命令残片和调度进程内存；新增 ext4 来源属性与独立公开投递 URL 完全相同；完整利用请求来源与操作者身份仍未确定，仅公开失活 IOC |

## 与参考项目的区别

参考对象固定为 [commit 130933a](https://github.com/soimy/c3rb3r-rescue/tree/130933a95bf823bafc998a9d122b055075660319)，避免把其后续更新混入本次核对。

| 事项 | 参考项目所述案例 | 本案 |
| --- | --- | --- |
| 内存来源 | PVE/QEMU 来宾 RAM | 所有者确认的物理机 DSM 内 `/proc/kcore` 顺序采集 |
| 加密器 | 有可分析的样本 | 后取得相同完整分析样本；NAS 当时全文件仍未恢复 |
| 恢复材料 | 找到并验证了 48 字节材料 | 测试公开候选及本机候选，均未得到有效解密 |
| 文件尾标记 | `ce35a593` | 扩大语料中 24,120 份不同有效文件尾均为 `6d147f60` |
| 实际结果 | 其案例有备份和应用层验收 | 本案以残存数据提取为主，尚无整库或整套业务恢复证明 |

相同勒索信、后缀或疑似漏洞不代表相同样本和密钥。参考项目的成功不能代替本机验证。其工具只对其已分析样本和格式作出说明；本仓库不附带通用解密器。

另已核对 [Benjamin-zlt/c3rb3r-baremetal-rescue](https://github.com/Benjamin-zlt/c3rb3r-baremetal-rescue/tree/906e81293153341f162ee1f176722d93ba1d8358) 的物理机成功案例：5 项自测通过，但其原版解析器使用另一案例的公开材料检查本机 24,120 份文件尾，全部未通过 nonce 校验。其成功前提是保留了本机仍存活的加密进程及其内存。

## 当前能说到什么程度

固定清单包含 **19,916 个输出对象**，其中大量是 ZIP 内部成员、Office 组件、地图区域或音视频片段。后续任务另一次检查记录到 **60,924 个输出对象**，仍在增长，尚未逐个完成同等深度的可用性检查。两批统计范围不同，不相加，也不据此计算成功率。

**20:20 保存的状态记录为 547,993 个输出对象，源归档任务完成 252/431。** 这个计数包含成员、组件和片段，未新增同等规模的完整原文件验收；它不与前面两次计数相加。

**22:46:35 的保存记录为 885,014 个输出对象，274/431 个源归档任务完成；原恢复服务正在跨卷迁移已恢复副本，记录已迁移 21,565 个对象、11,840,542,306 字节。** 这是当时的状态，不代表当前实时值，也不代表完整原文件数量。

已完成的检查包括归档成员 CRC、部分格式结构检查、5 个 MP4 的全程解码抽样，以及地图区块解压和坐标检查。缺少原始明文摘要、应用验收或人工内容对照的对象，其语义完整性仍未得到证明。详细数量与限制见[恢复结果](docs/recovery-results.md)。

这是已发生事件的记录。现场没有完成全盘镜像，后期还在原 NAS 上运行恢复服务并写入新目录；此举有原卷写入成本，不能称为完全只读、离线取证或通用最佳实践。Git 历史仅含独立撰写的文档和脱敏事实摘要，不包含内存、会话密钥、账号或业务文件；独立 Release 中的恶意研究样本按上述后续授权单独发布。
